# Правила для ИИ, который пишет код этого проекта

Этот файл читается первым. Он важнее любых привычек и умолчаний.

## 0. Контекст

Владелец проекта не программист. Он читает код, но не пишет его. Значит:

- каждый ответ содержит точные команды, которые нужно выполнить, и что должно появиться на экране;
- никаких шагов вида «настройте в редакторе» — всё делается кодом и командами;
- если что-то сломалось, сначала диагностическая команда, потом правка.

## 1. Порядок работы

1. Прочитать `docs/DESIGN.md` и текущий срез в `docs/PLAN.md`.
2. Делать **только текущий срез**. Не забегать вперёд, не добавлять системы из будущих срезов «пока рядом».
3. Срез считается закрытым, когда выполнены все критерии приёмки из `docs/PLAN.md` и владелец подтвердил это на запущенном exe.
4. Спорные решения по геймдизайну не выдумывать. Записать вопрос в `docs/QUESTIONS.md` и предложить два варианта.

## 2. Технические рамки

- Язык: C#, последняя LTS .NET. Фреймворк: MonoGame DesktopGL.
- Внешние NuGet-пакеты запрещены без явного согласования. Исключения: тестовый раннер и `System.Text.Json`.
- Никаких игровых движков, редакторов сцен, визуальных скриптов.
- Никаких бинарных ассетов в git: спрайты, тайлы и анимации генерируются кодом при старте.
- Интерфейс только на русском. Все строки живут в `data/strings.ru.json`, в коде только ключи.

## 3. Структура репозитория

```
src/
  WorldBox.Core/      симуляция. НЕ ЗНАЕТ про графику, окно, ввод
  WorldBox.Render/    рисование, атласы, процедурный арт
  WorldBox.UI/        панели, инспектор, летопись
  WorldBox.Desktop/   точка входа, игровой цикл, ввод
  WorldBox.Bench/     консольный прогон симуляции без окна
tests/
  WorldBox.Tests/     юнит-тесты ядра
data/                 json-данные: эпохи, ресурсы, религии, строки
docs/                 документация
```

Железное правило: `WorldBox.Core` не ссылается на MonoGame. Симуляция должна прогоняться в консоли без окна. Это даёт быстрые тесты и честный замер производительности.

## 4. Правила производительности

Это симулятор, а не платформер. Производительность — часть дизайна.

- Данные мира хранить массивами примитивов (structure of arrays), не списками объектов. `float[] elevation`, `byte[] biome`, `int[] owner`.
- В горячих циклах запрещены: LINQ, `foreach` по интерфейсам, боксинг, `string` конкатенация, аллокации.
- Ноль аллокаций за кадр в цикле рендера. Все буферы выделяются один раз.
- Тяжёлые проходы по карте распараллеливать по чанкам через `Parallel.For`, но результат сводить детерминированно.
- Каждый срез заканчивается замером: `dotnet run --project src/WorldBox.Bench -- --ticks 5000`. Результат вписывается в `docs/PERF.md`.

Бюджет кадра при 60 fps (16.6 мс):

| Этап | Бюджет |
| --- | --- |
| Симуляция за кадр | 6 мс |
| Подготовка отрисовки | 3 мс |
| Рисование | 5 мс |
| Интерфейс | 2 мс |

## 5. Детерминизм

- Единственный источник случайности — класс `Rng` (xorshift128), инициализируется сидом мира.
- В симуляции запрещены `DateTime.Now`, `Random`, `Guid.NewGuid`, обращения к сети и файлам.
- Один и тот же сид и одинаковое число тиков дают одинаковый мир. Это проверяется тестом `DeterminismTests`.

## 6. Время и тики

- Симуляция идёт фиксированным шагом 20 тиков в секунду и не зависит от fps.
- Скорости: пауза, x1, x4, x16, x64. Быстрые скорости прогоняют больше тиков за кадр, но с жёстким лимитом по времени: если не успели, кадр всё равно рисуется.
- Системы внутри тика выполняются в фиксированном порядке, он задан в `SimulationLoop.cs` и не меняется без причины.

## 7. Данные вместо констант

Любое число, которое влияет на баланс, живёт в json: эпохи, ресурсы, скорость роста населения, смертность от чумы, цены. В коде читается один раз при старте. Магические числа внутри систем запрещены.

## 8. Правила коммитов

- Одна задача — один коммит. Формат: `s4: диффузия технологий между соседями`.
- Перед коммитом: `dotnet build` без предупреждений и `dotnet test` зелёный.
- Не коммитить `bin/`, `obj/`, сохранения, скриншоты.

## 9. Как отчитываться перед владельцем

После каждого куска работы:

1. Что сделано в одном абзаце простым языком.
2. Команда для проверки.
3. Что именно он должен увидеть на экране.
4. Что сломается, если этого не сделать правильно.
